Platform observability

System tables feed one dashboard for runs, failures, cost, compute, and audit events, and a SQL alert emails the owner.

The short version

  1. System tables are the source.

    Four system schemas cover runs, usage and price, compute events, and audit. Nothing is collected by hand.

  2. A snapshot job turns them into ops tables.

    Five SQL tasks write ops_* tables, and a setup task adds ops_alert_routing from the Jobs and Alerts APIs. The dashboard and the alert read these small tables, not raw system tables.

  3. One dashboard has six pages.

    Runs, Failures, Usage and cost, Compute and capacity, Audit events, and Alert routing, plus a Filters page.

  4. One alert watches failures.

    It counts failed guide-job runs in the last 24 hours, is evaluated hourly, and emails the owner when the count is above 0.

  5. Routing is itself on a page.

    The Alert routing page lists who would be told for each job and alert, and shows alerts nobody receives.

From system tables to one dashboard

The snapshot job copies a window of each system table into a small ops_* table. The dashboard reads only those. The routing table is the odd one out: system tables do not hold email notifications, so it comes from the APIs.

What each dashboard page shows

One page per question, each backed by one ops table. A Filters page scopes the whole dashboard to capability guide jobs, a use case, and a date range.

The alert path

A SQL alert runs a count over ops_failures every hour. If the count is above 0, it emails the owner. If not, it stays quiet.

Healthy versus failure fired

The same three steps run in both cases. Only the count changes, and with it whether anyone is emailed.

Who owns the alerts, and how you can see it

One address, alert_email, receives three things. A separate path records every notification destination so the Alert routing page can show who would be told.

Demo steps

  1. Run the snapshot job. It refreshes the five SQL-task tables and builds the routing table. Run lookback is 14 days, audit lookback is 7.
  2. Open the dashboard. Walk the Runs, Failures, Usage and cost, Compute and capacity, and Audit events pages.
  3. Use Filters. Scope to capability guide jobs, one use case, and a date range.
  4. Open Alert routing. Show each job and alert destination, and point at any row with destination type none.
  5. Show the alert query. It counts failed guide-job runs in the last 24 hours and fires above 0. Healthy means no email.
  6. Show a failure. After a guide job fails and the next snapshot lands, the hourly check fires and the owner gets an email.
