Configuration-driven ingestion

Two providers land through one shared framework. Only a feed config and a 20-line adapter differ between them; validation, quarantine, audit, and error handling are shared.

The short version

  1. A provider is a YAML file and a small adapter.

    The feed file names the format, column mapping, key, and validation rules. Provider A also has about 20 lines of Python to decode its single-letter status codes. Provider B needs no Python at all.

  2. Everything else is written once.

    runner.py, validation.py, and audit.py serve every feed. They contain no per-provider branches.

  3. One job task runs every feed.

    A for-each task runs run_feed.py once per feed. Adding a feed adds an input, not a task.

  4. Bad rows and failures are contained.

    Rows that break a rule go to transactions_quarantine with the names of the rules. A failed run is written to audit_log and then re-raised, so job retry and alerts apply.

Error handling is also shared. A failure is written to audit_log first, then raised again, so the job's own retry and alert settings still do their work.

Demo steps

  1. Show the two feed files. Compare provider_a.yml and provider_b.yml. Only format, mapping, and adapter name differ.
  2. Show the adapter. Open adapters/provider_a.py and point at the status-code table. Provider B has no adapter file of its own.
  3. Show the shared modules. Open runner.py, validation.py, and audit.py. None of them mention a provider by name.
  4. Show the job. One for-each task, ingest_each_feed, runs run_feed.py per feed.
  5. Query the evidence. Select from audit_log and from transactions_quarantine grouped by source_feed to show the counts above and the rule names.
