Batch and streaming ingestion

A batch framework run and a streaming Lakeflow pipeline share one job. Auto Loader picks up new files, expectations drop bad rows, and latency is measured per row.

The short version Batch path Streaming datasets One flag, two modes What changes and what stays Reference run Where it lives

The short version

  1. Batch is the framework plus a materialized view.

    The batch_ingest task runs the configuration-driven ingestion job into transactions_silver. A materialized view, transactions_daily_summary, aggregates it per feed and currency.

  2. The streaming side is a serverless Lakeflow Declarative Pipeline.

    Auto Loader reads new event files into events_bronze. events_silver applies expectations and computes latency_seconds per row.

  3. One key flips the mode.

    continuous in resources/streaming.pipeline.yml is false in the repo. Set it to true and the same datasets run continuously.

  4. Triggered numbers are measured. Continuous numbers are not yet.

    The reference run recorded p50 latency of 124 s in triggered mode. No continuous run, scaling run, or live monitoring is recorded, and this page says so.

The batch path

The first task of the job, batch_ingest, runs the whole ingestion framework as a child job. Its output feeds the daily summary.

The streaming datasets

The job lands event files, then starts the pipeline. Inside the pipeline, Auto Loader picks up only new files, so a rerun grows bronze by exactly one run's events.

One flag, two modes

In resources/streaming.pipeline.yml, continuous: false means the job starts an update, the update drains the new files, and it stops. With continuous: true the pipeline stays up and handles files as they arrive.

What changes and what stays

Flipping the flag changes when the pipeline runs. The datasets, the SQL in them, and the compute settings are the same in both modes.

What the reference run measures

Solid boxes are numbers from the triggered-mode reference run, read from the pipeline's own tables. Dashed boxes are next steps the reference run does not cover.

Demo steps

  1. Open the job. capability-guides-batch-real-time has four tasks: batch_ingest, land_stream_events, streaming_pipeline, then record_metrics.
  2. Show the batch result. Query transactions_daily_summary, the aggregate over transactions_silver.
  3. Rerun and compare bronze. Auto Loader reads only new files, so events_bronze grows by exactly one run's events.
  4. Show expectations and latency. Open events_silver for the dropped rows and latency_seconds, then ingestion_latency_by_minute for p50, p95, and max.
  5. Say what is not shown. Continuous-mode latency, autoscaling, and live monitoring have no recorded run yet.
