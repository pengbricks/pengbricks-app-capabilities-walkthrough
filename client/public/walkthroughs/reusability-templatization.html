The short version

  1. A second feed is a block in one spec file.

    Provider B is a provider_b block in use_cases/general.yml: format, source columns, mapping, and adapter: generic. No Python file is added.

  2. A renderer writes the feed config.

    tools/render_use_case.py turns the spec into feeds/general/*.yml. With --check it fails if the committed feeds have drifted from the spec.

  3. The framework does not change.

    The runner, validation, audit, and output tables are the same whether one feed or two are registered. The job iterates over the feed list, so a new feed adds an input, not a task.

  4. The generic adapter handles the mapping.

    It reads the files with the configured options and applies the configured column expressions: renames, casts, nested fields.

  5. The same rules and audit apply automatically.

    Both feeds produce one audit_log row each and quarantine rejected rows through the same shared rules.

What onboarding changes in the repo

Adding provider B touches the spec and produces one generated feed file. Every framework file stays exactly as it was, so the review is one small diff.

One feed registered, then two

Compare the two frames. The dashed config boxes on the left side of each frame grow from one to two. The runner and the tables on the right are the same objects.

From one spec to the feed configs

Nobody edits the feed files by hand. They are generated from the use-case spec, and a drift check keeps the committed files honest.

How the generic adapter maps columns

Provider B's JSON has nested fields and different names. Each canonical column is one SQL expression in the config, applied by generic.py.

Both feeds, same rules

One job run produced one audit_log row per feed. Provider B uses no custom adapter, yet its rows are validated and quarantined by the same rules.

Demo steps

  1. Open the spec. In use_cases/general.yml, find the provider_b block. It holds the source shape and the mapping, with no code.
  2. Run the drift check. python tools/render_use_case.py use_cases/general.yml --check confirms the committed feed configs match the spec.
  3. Show the diff for a third feed. Copy the provider_b block, rename it provider_c, change the format and mapping, and rerun the renderer. No Python changes.
  4. Open the latest framework run. land_files sets the task value feeds from the spec, and ingest_each_feed iterates over it.
  5. Compare the feeds. The compare_feeds output shows the same columns and the same rules for both.
